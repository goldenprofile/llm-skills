# Policy и canonical-документация

Policy — карта на 1–2 экрана, не энциклопедия. Дублировать в ней то, что проверяет CI, нельзя.

## Слои памяти (куда что класть)

Инструкции, которые пишешь ты, и заметки, которые агент ведёт сам, — **разные системы**.
Обе грузятся в начале сессии.

**Инструкции (пишешь ты), в порядке загрузки — от общего к частному:**

| Слой | Файл | В git? | Что туда |
|---|---|---|---|
| Организация | managed policy (`/etc/claude-code/CLAUDE.md` и аналоги) | ❌ | политики компании; отдельным проектом не отключается |
| Личное, на все проекты | `~/.claude/CLAUDE.md` | ❌ | язык, роутинг навыков, среда своих машин (ОС/шелл, где крутятся сервисы) |
| **Проект, переносимое** | `./CLAUDE.md` или `./.claude/CLAUDE.md` | ✅ | что за проект, рантайм (OS-агностично), tooling, DoD, инварианты, Canonical Docs |
| Проект, по путям | `.claude/rules/*.md` | ✅ | правила, нужные не всегда (см. ниже) |
| Проект + эта машина | `./CLAUDE.local.md` | ❌ (gitignore) | проектно-машинное, что не должно попасть в репо |

**Главное правило:** committed `./CLAUDE.md` обязан быть **переносим** — открой его на другой ОС,
он не должен противоречить. Машинно-специфичное (конкретная ОС и оболочка, «сервисы на удалённом
хосте», `systemctl`) → в `~/.claude/CLAUDE.md` или `CLAUDE.local.md`, **не в репо**. Рантайм
формулируй как факт проекта: «нужны Postgres+Redis; `test`/`migrate` → CI/окружение с БД», а не
как факт о чьей-то рабочей машине.
`CLAUDE.local.md` не устарел и поддерживается — добавь его в `.gitignore`.

### `.claude/rules/` — правила, которые грузятся по путям

Вместо того чтобы держать всё в одном раздутом `CLAUDE.md`, вынеси тематические правила в
`.claude/rules/*.md`. Файл с frontmatter `paths:` попадает в контекст **только когда агент
работает с подходящими файлами** — это дешевле, чем платить за них каждую сессию:

```markdown
---
paths:
  - "apps/**/migrations/*.py"
---
Миграции: до применения на проде — навык migration-safety-auditor.
```

Без `paths:` файл грузится всегда, наравне с `.claude/CLAUDE.md`. Личные правила на все
проекты — `~/.claude/rules/`.

Ориентир по размеру: **≤ 200 строк на файл**. Длиннее — хуже соблюдается, а не просто дороже.

### Auto memory — то, что агент пишет себе сам

Отдельная система: `~/.claude/projects/<project>/memory/` с индексом `MEMORY.md`, включена по
умолчанию (`autoMemoryEnabled`). Агент сам складывает туда находки — команды сборки, грабли,
предпочтения. В каждую сессию грузятся первые 200 строк / 25 КБ `MEMORY.md`; тематические файлы
рядом читаются по требованию. Каталог машинно-локальный и общий для всех worktree одного репо.

Для harness это значит: **факты о проекте, которые агент способен обнаружить сам, не надо
вписывать в `CLAUDE.md` руками** — он их запомнит. В committed policy держи то, что решено
людьми и должно быть одинаковым у всех: DoD, MUST NOT, tooling, инварианты.

## CLAUDE.md + AGENTS.md (canonical — там, где его читают все)

Claude Code читает `CLAUDE.md` и **не читает** `AGENTS.md`; OpenCode и многие другие агенты —
наоборот. **Не веди копию и не полагайся на симлинк** (копия разъезжается; симлинк переносим не
на всех ОС).

Правильное направление — **canonical `AGENTS.md`**, а `CLAUDE.md` подтягивает его импортом:

```markdown
@AGENTS.md

## Claude Code
<если нужно — специфика только для Claude Code, ниже импорта>
```

Так содержимое видят обе стороны. Обратная схема (правила в `CLAUDE.md`, а в `AGENTS.md` —
строчка «см. CLAUDE.md») выглядит симметрично, но оставляет других агентов **без правил**:
они прочитают указатель на файл, который не открывают. Если в проекте только Claude Code —
держи всё в `CLAUDE.md` и не заводи `AGENTS.md` вовсе.

Перенести конфиг другого агента разово помогает `/import`.

**Длинные доки — импортом, не копипастой.** В `CLAUDE.md` подключай через `@path` (раскрывается в
контекст, относительные пути — от файла-источника, до 4 уровней рекурсии, в backticks не
раскрывается):

```markdown
@ARCHITECTURE.md
@docs/ROADMAP.md
```

## Hooks + permissions (enforcement, не зависящий от памяти агента)

`.claude/settings.json` (project-уровень, коммитится) — слой, который **не даёт забыть** прогнать
проверки, в отличие от Makefile, который агент должен вспомнить запустить:

```jsonc
{
  "permissions": {
    "allow": ["Bash(make lint:*)", "Bash(make format-check:*)", "Bash(make type:*)", "Bash(uv run:*)"]
  },
  "hooks": {
    "PostToolUse": [
      { "matcher": "Write|Edit",
        // путь изменённого файла хук читает из JSON на stdin (.tool_input.file_path)
        "hooks": [{ "type": "command",
          "command": "f=$(jq -r '.tool_input.file_path'); uv run ruff check --quiet \"$f\"" }] }
    ]
  }
}
```

- `PostToolUse` на `Write|Edit` → линт изменённого файла сразу после правки (результат уходит агенту).
- `PreToolUse` может **блокировать** — например, не дать закоммитить с плохим сообщением или
  применить миграцию без прогона `migration-safety-auditor`. Два способа: `exit 2` (блокирует
  всегда, что бы ни было в stdout) или JSON, где решение лежит **внутри `hookSpecificOutput`** —
  без этой обёртки хук молча не сработает:

  ```json
  { "hookSpecificOutput": { "hookEventName": "PreToolUse",
      "permissionDecision": "deny",
      "permissionDecisionReason": "Миграция без прогона migration-safety-auditor" } }
  ```
  Что осмысленно закрывать deny-хуком (**статикой**, без модели-классификатора — он избыточен, у
  агента уже есть встроенное одобрение), по категориям риска:
  1. **необратимое разрушение / эксфильтрация** — `rm -rf`, `git push --force`, `DROP`/`TRUNCATE` на проде, выгрузка секретов наружу;
  2. **деградация security-постуры** — снос линтеров/хуков, `--no-verify`, отключение CI-гейтов, ослабление прав;
  3. **пересечение границы доверия** — обращение во внешнюю сеть с секретами, `curl … | sh`;
  4. **обход ревью / влияние на чужое** — коммит мимо DoD, правка чужих веток.
- `permissions.allow` снимает промпты на безопасных целях; быстрый старт — `/fewer-permission-prompts`.
  Держи allowlist **узким** (конкретные `make`/`uv run`-цели, не широкий `Bash(*)`): слишком широкий
  allow → агент штампует подтверждения не глядя, и слой перестаёт защищать.
- Машинно-личные allow/hooks → в `~/.claude/settings.json`; `.claude/settings.local.json` (gitignored)
  — для машинных оверрайдов.

**События, кроме двух основных.** Их около трёх десятков; для harness обычно полезны:

| Событие | Зачем в обвязке |
|---|---|
| `Stop` / `SessionEnd` | финальный гейт: прогнать `make lint`/`type` в конце хода, а не надеяться, что агент вспомнит |
| `InstructionsLoaded` | залогировать, какие CLAUDE.md и rules реально загрузились — этим отлаживают «правило есть, но не соблюдается» |
| `PostToolUseFailure` | реакция на упавший инструмент (например, подсказать агенту про нужный сервис) |
| `PreCompact` / `PostCompact` | сохранить и вернуть контекст вокруг компактификации |

Полный список событий и схему вывода сверяй с docs Claude Code — они пополняются.

## Шаблон policy-файла (CLAUDE.md / AGENTS.md)

```markdown
# <Проект> — заметки для агента

## Tooling
make lint | make format | make type | make test | make sec | make check
(make кросс-платформенный)
В сессии: pyright-lsp (типы) · /code-review + /security-review (быстрые гейты диффа)

## MUST NOT
- Не применять миграции на проде без прогона навыка migration-safety-auditor
- Не редактировать уже применённые миграции
- Не коммитить секреты; конфиг — через env, не в репозиторий
- <короткие проверяемые запреты под конкретный проект>

## Definition of Done
Автоматика: make check — зелёный (lint, type, test, sec); типы в сессии — pyright-lsp.

Перед каждым коммитом (быстрые гейты диффа):
1. /code-review — баги + переиспользование/упрощение (--fix применяет правки)
2. /security-review — безопасность диффа
3. коммиты — по git-commit-planner

Перед релизом / по запросу (глубокие навык-гейты):
4. test-coverage-auditor — качество тестов (assertion'ы, моки)
5. migration-safety-auditor — если затронуты миграции, до деплоя
6. change-review — глубокое ревью на крупном/рискованном диффе (вызывать явно)
7. python-project-audit — production readiness (для Django — django-audit, security-линза)

(Слэш-команды — гейты Claude Code; в OpenCode роль закрывают make sec + change-review/django-audit.)

## Canonical Documentation
- ARCHITECTURE.md — границы модулей, инварианты, reference-примеры
- tasks/lessons.md — накопленные грабли и правила
- WORKFLOW.md — оркестрация (только если включён Symphony)
```

Соло-нюанс: DoD — не пожелания, а конкретные вызовы. Быстрые гейты диффа — официальные команды
Claude Code (`/code-review`, `/security-review`), глубину и release-готовность дают твои навыки.
Harness здесь — оркестратор, поэтому policy остаётся коротким, а «как именно проверять» живёт
в навыках и командах.

## ARCHITECTURE.md

```markdown
# Архитектура

## Компоненты
<кратко: какие модули и за что отвечают>

## Границы и зависимости
<кто от кого зависит; зависимости однонаправленные>

## Инварианты
- <правила, которые ВСЕГДА соблюдаются — то, что агент не должен нарушать>

## Reference-примеры
| Паттерн | Эталонный файл |
|---------|----------------|
| Django-вью | app/views/orders.py |
| FastAPI-роут + Pydantic | app/api/orders.py |
| aiogram-роутер + FSM | bot/handlers/checkout.py |
```

## tasks/lessons.md

```markdown
# Lessons Learned
Цикл: ошибка агента → правило → проверка.

### [ГГГГ-ММ-ДД] Краткое описание
**Паттерн:** что пошло не так
**Правило:** что делать/не делать
**Проверка:** какой lint/тест/CI-шаг это ловит (если правило непроверяемо — сделать проверяемым)
```

Каждую пойманную в Фазе 4 проблему фиксируй здесь. Если правило нельзя привязать к
автоматической проверке — это сигнал добавить линт-правило или тест, а не просто текст.
