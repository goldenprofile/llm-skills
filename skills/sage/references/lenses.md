# Линзы SAGE

Линза — тип кейса. Выбери **одну** первичную. Второй линзой не прогоняй
процесс целиком: при необходимости добавь один артефакт из соседней
(например, development + `RUNBOOK.md`).

Сигналы ниже — эвристика, не чеклист. Смотри на вход, не на ключевые слова.

## development

Новая система или крупная фича с нуля: есть идея / черновик дизайна, кода
ещё нет или он не источник истины.

- **Команда (типично):** Backend + одна-две из {DevOps, Fullstack, QA, DBA}.
- **Артефакты:** Summary, Discussion, `SYSTEM_DESIGN.md`, `AI_AGENT_PROMPT.md`,
  `MILESTONES.md`.
- **О чём спорить:** стек, границы MVP, модель данных, API, что сознательно
  не делать. Не начинай с CI, пока нет ядра.

## hardening

Нужно обезопасить существующую или проектируемую развёртку: открытые порты,
агент с доступом к ОС, секреты, периметр.

- **Команда:** Security + DevOps + SRE.
- **Артефакты:** Summary, Discussion, `SYSTEM_DESIGN.md` (слои защиты),
  `RUNBOOK.md`, `CHECKLIST.md`. Threat model — секция дизайна или отдельный
  `THREAT_MODEL.md`, если модель большая.
- **О чём спорить:** attack surface, что закрыть в первую очередь, что
  оставить ради работоспособности. Не предлагай Kubernetes «для безопасности».

## audit

Разобрать текущее состояние и выдать выводы, а не спроектировать новое.
Вход — описание проблемы, скриншоты, конфиги, «как есть».

- **Команда:** по предмету (DevOps / Security / Backend / DBA), 2–3 роли.
- **Артефакты:** Summary, Discussion, `RECOMMENDATIONS.md`. Runbook и
  checklist — только если из аудита следует конкретное действие.
- **О чём спорить:** варианты «что делать дальше», цена/риск каждого.
  Не подменяй `django-audit` / `python-project-audit`: те читают код
  репозитория по чеклисту. Эта линза — когда кода мало или задача шире
  одного стека.

## migration

Перенос системы, данных, почты, панели, БД с сохранением работы.

- **Команда:** DevOps + SRE + профильная роль (DBA, mail, Security).
- **Артефакты:** Summary, Discussion, `RECOMMENDATIONS.md` (выбор цели),
  `RUNBOOK.md`, `MILESTONES.md`, `CHECKLIST.md`.
- **О чём спорить:** целевой стек, порядок переключения, rollback,
  что мигрировать нельзя / не стоит. Downtime — явное решение, не «посмотрим».

## ops

Операционный контур и tooling: деплой, наблюдаемость, релизы, как возить
код на сервер. Не «напиши unit-файл» (это `vps-ops`), а «какой должна быть
система деплоя».

- **Команда:** DevOps + SRE + Backend (сторона приложения: миграции,
  health, откат схемы).
- **Артефакты:** Summary, Discussion, `SYSTEM_DESIGN.md`, `RUNBOOK.md`,
  `MILESTONES.md`; `AI_AGENT_PROMPT.md` — если следующий шаг — реализация
  скриптов/конфигов.
- **О чём спорить:** ручной-но-правильный vs CI, атомарность релиза,
  кто владеет миграциями. Не прыгай через фазы «сразу Ansible».

## research

Сравнить подходы, ответить на «как лучше», без обязательства внедрять.

- **Команда:** 2–3 роли, чьи зоны затрагивают вопрос.
- **Артефакты:** Summary, Discussion, `RECOMMENDATIONS.md`.
- **О чём спорить:** критерии сравнения (явные), а не вкусовщина.
  Итог — рекомендация с отвергнутыми вариантами, не обзор ради обзора.
