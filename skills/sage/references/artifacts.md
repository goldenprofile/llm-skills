# Артефакты

Имена файлов — стабильный контракт. Не переименовывай (`TEAM_BRAIN_STORM.md`
больше нет — только `TEAM_DISCUSSION.md`).

Неприменимые секции опускай. Не пиши «N/A».

## Базовые (всегда)

### `PROJECT_SUMMARY.md`

Саммари, которое можно прочитать вместо всего пакета.

1. Название
2. Проблема (конкретно, не «хочется лучше»)
3. Решение (одним абзацем + чем не является)
4. Стек — таблица «слой / технология / зачем», без версий «latest» без нужды
5. Scope / out of scope
6. Архитектура верхнего уровня (ASCII или mermaid, без деталей реализации)
7. Риски — таблица: риск, влияние, смягчение
8. Оценка — диапазон, для кого считали, что не вошло

### `TEAM_DISCUSSION.md`

Протокол, не стенограмма. По каждому спорному вопросу:

- вопрос координатора
- позиции ролей (по абзацу, не эссе)
- решение + обоснование (ADR-lite)

В шапке: дата, линза, состав. Не дублируй саммари.

## Специализированные

Подключай по линзе из [lenses.md](lenses.md). Ниже — скелет, если артефакт
вошёл в набор.

### `SYSTEM_DESIGN.md`

Source of truth для реализации. Саммари его не подменяет.

1. Обзор и цели
2. Компоненты и связи (схема)
3. Модель данных **или** модель угроз — что является ядром линзы
4. API / интерфейсы / контракты (если есть)
5. Ключевые решения (ссылки на discussion, не копипаста протокола)
6. Деплой и эксплуатация — ровно столько, чтобы нельзя было «придумать на ходу»
7. Что сознательно не делаем

Правило: инженер, который не видел discussion, должен суметь реализовать
по этому файлу.

### `AI_AGENT_PROMPT.md`

Пошаговая инструкция исполнителю-агенту. Ты её **не выполняешь**.

- Роль исполнителя и ссылка: единственный SoT — `SYSTEM_DESIGN.md` / `RUNBOOK.md`
- Стек — таблица, строго
- Общие правила (типизация, тесты, логи, «не изобретай — спроси»)
- Фазы: цель, задачи, критерий «фаза закрыта», что нельзя начинать раньше
- Каждая фаза — проверяемый результат, не «настроить инфраструктуру»

Не копируй system design целиком. Проверяй, что фазы покрывают scope
и не залезают в out of scope.

### `MILESTONES.md`

Дорожная карта уровня дней/вех, не микротаски.

Для каждой вехи: цель, оценка-диапазон, зависимости, владелец (роль),
deliverables-чекбоксы, критерий завершения (команда/проверка, не «готово»).

Первая веха должна оставлять что-то работающее (скелет+health), а не только
репозиторий с конфигами.

### `RUNBOOK.md`

Для человека, который будет делать руками. Copy-paste шаги.

- Для кого и какой риск, если пропустить шаг
- Фазы с оценкой времени
- Команда → ожидаемый результат → типичная ошибка → откат
- Никаких «настройте по вкусу». Плейсхолдеры явные: `example.com`, `myapp`

### `CHECKLIST.md`

Приёмка. Группы чекбоксов, каждый пункт **проверяемый**
(`curl -I`, `systemctl is-active`, конкретный URL), не «сайт работает».

### `RECOMMENDATIONS.md`

Сравнение вариантов. На вариант: критерии, плюсы/минусы, стоимость/риск.
В конце — одна рекомендация и что делать, если её отвергнут.
Не прячь проигравшие варианты.

### `THREAT_MODEL.md` / `SECURITY_ARCHITECTURE.md`

Только если threat model не умещается в секцию дизайна.

- активы, акторы, attack surface
- угрозы и митигации по слоям
- что принимаем как остаточный риск (явно)

## Порядок записи

1. `TEAM_DISCUSSION.md` — пока решения свежие
2. Специализированные (design / recommendations / runbook)
3. `AI_AGENT_PROMPT.md` и `MILESTONES.md` — они опираются на design
4. `PROJECT_SUMMARY.md` последним: он сжимает уже принятое, а не наоборот
5. `CHECKLIST.md` — с runbook, чтобы пункты совпадали с шагами
